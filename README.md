# 学習ログ

未経験からエンジニアに転向し、バックエンド（Scala）と上流工程を軸に学習している記録です。
毎日何を学んだか、どこで詰まってどう解決したかを残しています。

- 学習ロードマップ: [ROADMAP.md](./ROADMAP.md)
- 読んだ本: [BOOKS.md](./BOOKS.md)
- 作ったもの: [PROJECTS.md](./PROJECTS.md)
- 日次ログ: [`logs/`](./logs/)
- 週次振り返り: [`weekly/`](./weekly/)

---

## このリポジトリの目的

**1. 自分で解決した記録を残す**

「詰まった → どう調べた → どうなった」を毎回書きます。これが積み上がることが、自分で前に進める力の証拠になります。

**2. 3ヶ月ごとに事実で振り返る**

記憶ではなく記録で「何に時間を使ったか」「何が完成したか」を確認し、学習の優先順位を組み替えます。

**3. 学んだことを言葉にする**

読んだだけ・動かしただけで終わらせないために、1日1つだけ「人に説明する形」で書きます。

---

## 運用ルール

### 書き方のルール

| # | ルール | 理由 |
|---|---|---|
| 1 | 学習した日は必ず書く。**5分で書ける量にとどめる** | 書くのが重くなると続かない |
| 2 | 「学んだこと」は**1日1つだけ**。人に説明する形で書く | 全部書こうとすると手が止まる |
| 3 | 書くために学習を止めない。学習の最後の5分で書く | ログが主役になったら本末転倒 |
| 4 | **空コミットや水増しはしない** | 連続日数より、週の合計時間と完成物のほうが意味がある |
| 5 | 数日空いたら、まとめて1件書いて再開する。**遡って埋めない** | 連続記録を守るために事実でないことを書かない |

### 見る指標

連続日数（草の本数）は目的ではありません。振り返るときに見るのはこの3つです。

1. **週の合計学習時間**（目標: 20時間）
2. **完成させたものの数**（[PROJECTS.md](./PROJECTS.md)）
3. **自分で解決できた件数**（週次振り返りに記録）

> 草の本体は自作アプリのコードのリポジトリです。この学習ログはその補助として置いています。

---

## 公開リポジトリなので守ること

このリポジトリは Public です。業務で学んだことを書く場面が必ず出てくるので、以下は例外なく守ります。

**書かないもの**

- 会社名、顧客名、プロジェクト名、担当者名
- 業務コードそのもの（社内リポジトリからのコピー）
- 社内リポジトリの URL、Slack やチャットの引用、設計書・画面のスクリーンショット
- 顧客の業務内容が特定できる記述（「〇〇業界の△△システムで」など）
- 未公開の製品・機能の情報

**書き方を変えれば書けるもの**

業務で詰まったことは、**技術の一般論に抽象化して**書きます。

| ❌ そのまま書く | ✅ 抽象化して書く |
|---|---|
| 「A社の受注APIで `Either` のネストが深くなって詰まった」 | 「`Either` を返す処理を複数つなげたときにネストが深くなる問題」 |
| （業務コードを貼る） | （自分で書き直した最小の再現コードを貼る） |

**迷ったら書かない。** 判断に迷うくらいなら Private なメモに残して、公開ログには書きません。ここを雑にやると、技術以前の信頼を失います。

## 使い方

### 今日のログを作る

```bash
./scripts/new-log.sh
# → logs/2026/08/2026-08-24.md が作られます

# 日付を指定する場合
./scripts/new-log.sh 2026-08-23
```

### 今週の振り返りを作る

```bash
./scripts/new-weekly.sh
# → weekly/2026-W35.md が作られます
```

### Makefile を使う場合

```bash
make log      # 今日のログを作る
make weekly   # 今週の振り返りを作る
```

> Windows の場合は Git Bash（Git for Windows に付属）で実行してください。
> `EDITOR` 環境変数を設定しておくと、作成後に自動で開きます（例: `export EDITOR=code`）。

### コミット

```bash
git add .
git commit -m "log: 2026-08-24 Scala の for 式と Either"
```

コミットメッセージの目安:

- `log: 2026-08-24 <学んだことの見出し>` — 日次ログ
- `weekly: 2026-W35` — 週次振り返り
- `books: 達人に学ぶDB設計 読了` — 読了リスト更新
- `roadmap: マイルストーン更新` — ロードマップ更新

## ログの書き方（記入例）

````markdown
# 2026-08-24 (月)

**学習時間**: 3.0h
**分類**: Scala / 個人開発

## 今日やったこと

- Scala 3 公式 Book の Chapter 4（First-Look at Types）を読んだ
- 自作アプリの ER 図をたたき台まで書いた

## 今日学んだこと（1つだけ）

> `for` 式は特別な構文ではなく、`flatMap` と `map` の糖衣構文だった。
> `for { a <- optA; b <- optB } yield a + b` は
> `optA.flatMap(a => optB.map(b => a + b))` に展開される。
> だから `Option` でも `Either` でも `List` でも `Future` でも、
> `flatMap` / `map` を持っている型なら同じ書き方ができる。

## 詰まったこと → どう調べたか → 結果

| 詰まったこと | 調べた方法 | 結果 |
|---|---|---|
| `for` 式の中で `if` が使えるのが分からなかった | 公式 Book の for-expressions の節 → `withFilter` の説明を読んだ | ガード条件は `withFilter` に展開されると分かった。`Option` にも `withFilter` があるので動く |
| `Either` を `for` で回すと型が合わなかった | 手元で最小コードを書いて型を確認した | 左側（エラー型）が揃っていないと合成できない。エラー型を共通の `sealed trait` にまとめる必要がある |

## 明日やること

- Chapter 5（Control Structures）を読む
- ER 図を正規化の観点で見直す
````

**「詰まったこと」の表は必ず埋めます。** ここが空の日は、たいてい理解した気になっているだけです。
