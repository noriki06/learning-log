## 今日学んだこと

サービスなどの「種類」を表す enum は、DB に保存するとき **case 名がそのまま保存される**書き方だった。

これには弱点がある: **case の名前を変えると、DB に保存済みの値と食い違って壊れる。**
しかも社内の教科書に「その書き方は危ない」と書いてあった。

そこで、**保存する値を名前と切り離して自分で書く方式**（EnumStatus）に変えて、マージまでした。

1. **技術的に良くても、採用されるとは限らない。**
   設計資料との食い違い・他の担当者のファイルへの影響など、
   「正しさ」以外の理由で決まることがある。

2. **書き方を変える提案は、コードを書く前にチームの合意を取る。**
   自分の担当ファイルでも、「書き方のルール」はチーム全体のもの。

3. **マージ済みを取り消すときは revert を使う。**
   履歴は消さず、打ち消しのコミットを重ねて PR でマージする。
   失敗も記録として残る（それでいい）。



## つまずき

## 使い分けの実際

| 何を表すか | 書き方 | 保存される値 | 実例 |
|---|---|---|---|
| **状態**（〜中、〜済み） | `EnumStatus[Short]`＋数値を明示 | 数値（-2, -1, 0, 1…） | `Survey.Status`（準備中/公開…）、`Kind`（回答形式） |
| **種類**（サービス、次元） | 素の enum＋`def code = toString` | case 名の文字列 | `Service`、`ServiceConfig.Key`、`Dimension` |
| **階層つきの種類** | trait＋親から code を合成 | `"親.子"` の文字列 | `Metric` / `MetricItem`（`"STRESS_STD.A_CAUSE"`） |

## なぜ状態は数値なのか

数値は**大小や符号に意味を持たせられる**から。
    IS_DELETED   = -2      ← マイナス = 終わった状態
    IS_ARCHIVED  = -1
    IS_PREPARING =  0
    IS_PUBLISHED =  1      ← プラス = 生きている状態

「生きているものだけ」を `WHERE code > 0` の1条件で引ける。
状態には順序があるので、数値が向いている。

## なぜ種類は文字列なのか

種類には順序がなく、代わりに **DB を直接読めること**が大事だから。

    | 契約         | ← 数値なら
    | 2            |    「2って何？」とコード表を引く羽目になる
    | 契約         | ← 文字列なら
    | STRESS_CHECK |    見ただけで分かる

運営が SQL でデータを直接確認する運用なので、これが毎日効く。

## 注意点（このプロジェクトの約束）

- 文字列コード方式は **case を改名すると保存値も変わってしまう**。
