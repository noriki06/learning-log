## 今日学んだこと

> ライブラリから道具を「写す」前に、**もう入っていないか**を先に見る。
>
> 隣のプロジェクトが自前で持っていると思っていた窓口の書き方（5 段の DSL）を、自分のアプリ（myapp）に写そうとした。
> 調べたら DSL 本体は依存しているライブラリの jar に入っていて、基底クラスが `export` で丸ごと出していた。
> 自前なのは、その上に載せた薄い部品（認証の鎖・Option の持ち上げ・文言キー）だけで、写す範囲は思っていたより小さかった。
>
> 「あのプロジェクトにある＝あのプロジェクトが書いた」ではない。基底クラスの export と jar の中身を見てから、写す範囲を決める。

## つまずき

- Controller の中で `Event` と書いたら、import したモデルではなく、基底クラスから継承したイベントストリーム用の `Event` に解決された。
  import しているのになぜ、と思ったけど、Scala では継承で手に入る名前のほうが import より強い。
  モデル側を `Event as EventModel` と別名で import して回避した。

- 次からは、基底クラスの持ち物と同じ名前のモデルは、最初から別名で import する。

- **GitHub Actions の `pull_request_target` が 12/2 から公開リポジトリで既定ブロックに**（11/2）
  `pull_request_target` は、他人からの PR をきっかけに「元のリポジトリの権限」でワークフローを動かせるイベントで、悪用されやすい。GitHub はこれを 2026-12-02 から公開リポジトリで原則止める（元は 11/2 予定）。11/9 と 11/16 の 16:00〜18:00 UTC に予行演習の停止がある。
  公開リポジトリで Actions を使っているなら、このイベントを使うワークフローが無いかを先に確かめ、必要なものだけポリシーで明示的に許可する。
  https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2
