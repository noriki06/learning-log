# 2026-09-01 (火)

## 今日学んだこと

> **「危ないときは動かない」コマンドを選ぶと、中身を確かめずに毎日打てる。**
> `git merge --ff-only` は早送りできないとき、マージせずに失敗して止まる。
> `git branch -d` は取り込み済みでないブランチを消さない。
> どちらも**取り返しのつかない側に倒れないように作られている**。
> だから「これ打って大丈夫か」を毎回考えなくていい。

朝いちで develop を最新にする手順を、1つずつ何をしているか確かめたのがきっかけ。
今まで何となく打っていた3行の意味がつながった。

## 3行が何をしているか

    git checkout develop                 作業場所を develop に移す
    git merge --ff-only origin/develop   取ってきたものに追いつく
    git branch -d <ブランチ名>            用済みの札を外す

### なぜ `--ff-only` を付けるのか

早送り（fast-forward）できるのは、**自分の develop が相手の一部でしかない**とき。
このときのマージは、単に札を先へ動かすだけで、新しい履歴は生まれない。

早送りできない = **どこかで分岐している**ということ。
`--ff-only` を付けないと、Git はそこで勝手にマージコミットを作って履歴を混ぜる。
付けておくと、**混ぜる前に失敗して止まってくれる**。
自分の develop は「上流を写すだけの場所」なので、分岐しているなら、それ自体がおかしい。

### なぜ `-d` で消しても何も失われないのか

ここが今日いちばん腑に落ちたところ。

**ブランチはコミットを指す札でしかない。** 中身を持っていない。
札を外しても、そのコミットが develop の履歴に含まれていれば、中身はそのまま残る。

    develop ──●──●──●──●     ← ここに全部入っている
                        ↑
                    feature（札）    ← これを外すだけ

`-d` は「含まれていること」を確認してからでないと外さない。
含まれていなければ**拒否する**（強制する `-D` は別物）。
不安なら、消す前に develop との差分がゼロであることを見れば足りる。

## 前に学んだこととつながった

昨日は「取り返せない側に倒れる自動化は、精度をどれだけ上げても入れるべきではない」。
今日のこれは、**道具の側にも同じ設計がある**という話だった。

- `--ff-only`: 履歴を混ぜそうなときは動かない
- `-d`: 中身が消えそうなときは動かない

**危ない操作を拒んでくれる道具を選べば、注意力を使わずに済む。**
気をつけて打つのではなく、気をつけなくていい打ち方にする。

## ブランチの単位を切り直した

作業していたブランチの名前と、実際にやっている内容が合っていなかった。
最初に切ったときの見込みのまま、別のことをやり続けていた。

そこで、**降ってくる作業の単位＝ブランチの単位＝PR の単位**に揃えた。
今日は結果として5本の PR に分かれた。1本ずつが小さく、
名前がそのまま「何をしたか」の説明になるので、後から履歴を追える。

作業前にブランチを切り直すのは1分もかからない。
合っていない名前のまま進めるほうが、あとで高くつく。

## つまずき

**参照先のモデルがまだ無くて、コンパイルが通らなかった。**

新しく書いたモデルが、別のモデルの ID を持つ設計になっていた
（`Order` が `customerId` を持つような形）。
ところが参照される側がまだ実装されておらず、そこでコンパイルが止まった。

迷ったのは2つ。

| | やり方 | 抜けたときどうなるか |
|---|---|---|
| 案1 | 参照している項目を消して、後で足す | **エラーが出ない。**足し忘れても静かに動く |
| 案2 | 参照される側を仮で作る | 正式版に置き換えるとき、必ず目に入る |

案1は「後で足す」が抜けたときに気づけない。案2を選んだ。

そのうえで、**既存のモデルから項目を削っただけの仮実装にはしなかった。**
それだと何が仮で何が本物か分からなくなる。自分で考えた形で置き、
コミットメッセージと PR に「仮実装」と明記して、履歴に残した。

正式な設計はまだ来ていないので、**これは解決していない。**
置き換えるときに、仮のまま残っていないかを確認する必要がある。

**あわせて、プッシュの前にコンパイルを通す、を自分のルールにした。**
通らない状態を共有すると、次に取った人がまず自分の環境を疑うことになる。
壊れているものを渡さない、というだけの話だけど、今日それで一度止まった。
