## 今日学んだこと

- 認証の秘密は「自分の DB に持たない」側へ倒す。PIN ログインで DB が持つのは
  VerifyPinPayload(username, session) だけ — PIN 自体の生成・送信・照合は Cognito の
  custom auth に任せ、こちらは「回答に必要なもの」しか保存しない。漏れて困るものを
  最初から預からなければ、守る仕事も消える。Account.token の差し替え＝他の全端末の
  強制サインアウト（1トークン＝1セッション）も同じ発想で、状態を増やさず事実の入れ替えで制御する。

## 分かったこと
- app-api は app-lib を publishLocal 経由で参照（"engage-one" % 2.0.0-SNAPSHOT）。
  開発サイクルは「app-lib を変える → sbt publishLocal → app-api で sbt run」。
- 上位コンテキストの package.scala に Module（配下の persistence Module を install）と
  RepositoryFacade（束ね）を置く形。呼び出しは repos.iam.auth.account.…。
  コンテキスト追加は package.scala の 2 箇所＋reference.conf 1 行で済む。
- Cookie は 3 枚で役割分離: jwt_access（認証の本体）／token_refresh（再発行専用・認証には使わない）／
  selected_oid（操作中の法人。署名付きでも毎リクエスト所属を再検証してから信じる）。
- Employee.filterByAccountId が Seq を返すのは、法人をまたいで同じアカウントを使い、
  異動で旧行が残るから。戻り値の型が業務ルールを語っている。
- ボスは PIN 認証を一度フル実装してから「作り直すため」に 521 行削除し、配線だけ残した。
  参考書は履歴にある（git show 6a256d9）。ログインはアカウントを作らない（未紐付けは 403）、
  refresh token の保存は未実装、まで Scaladoc に明記されていた。
